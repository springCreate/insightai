我叫常奥青，软件工程背景转型 AI 产品方向。 最近在做一个叫InsightAI的项目——帮产品经理把一个产品想法在 1 分钟内变成结构化的洞察草稿，用 AI 解决早期决策缺数据、分析慢的问题。 → 说完立刻补一句："我对 AI 产品的可信度和边界设计比较感兴趣"

1分钟标准版 背诵

我叫常奥青，软件工程背景，之前做过 AI 对话助手的全流程产品。 InsightAI是我最近在做的另一个 AI 产品——面向产品经理的分析工具。 核心解决一个痛点：产品经理做早期方向判断时，缺数据、缺方法、汇报难。 我们的做法是把"想法 → 结构化洞察"压缩到 1 分钟， 输出市场分析、用户画像、RICE 优先级、MVP 路线图、成功指标和风险核验这 7 个维度。 我在项目里主要关注两件事： 第一是 AI 产品方法论——怎么把 TAM/RICE/OKR 这些框架产品化，让用户不用学就能用； 第二是无幻觉边界设计——AI 草稿不是事实，必须标注来源、假设、置信度，并提供证据驱动模式让用户手动核实。 → 等面试官追问："具体怎么做的？"

项目深挖：InsightAI
面试官一定会问的 5 个维度，每个都要能讲 2-3 分钟

2.1 项目背景与定位 背诵

痛点：PM 做早期方向判断时—— • 缺数据：中小团队没有数据/用研资源 • 缺方法：知道 RICE/OKR，但不会套用到具体想法 • 缺闭环：分析结果不成体系，难用于汇报 定位：不是一个 AI 聊天工具，而是 PM 分析工作流的产品化 → 用户不需要懂 Prompt 工程 → 不需要懂 RICE/OKR/TAM → 工具替他们完成 一句话：帮 PM 把"产品想法"变成"结构化洞察草稿"， 1 分钟替代 2-4 周的传统分析流程

2.2 最难决策：产品边界 STAR

场景：InsightAI 应该做"AI 聊天增强版"还是"PM 分析工具"？

S - Situation 项目早期，我面临一个选择： 要么做一个"内置 PM Prompt 的 AI 聊天"——开发快，但差异化弱； 要么做一个"PM 分析工作流"——要设计框架、结构化输出，但壁垒更高。 T - Task 我需要决定：核心价值是什么？差异化在哪里？ 不能让 InsightAI 变成"套壳 ChatGPT"。 A - Action 我做了三件事： 1. 竞品对比：横向对比 ChatGPT/Notion AI/咨询报告， 发现通用 AI 的问题是——输出不稳定、需要自己写 Prompt、没有产品化框架 2. 用户访谈（3人）：问 PM 朋友"你会用 AI 做产品分析吗？"， 得到的回答是——"我想要一个填完就出结果的东西，不想跟 AI 来回聊" 3. 框架设计：把 TAM/SAM/SOM、RICE、OKR 这些 PM 方法论拆解成 7 个结构化输出模块 R - Result 结论：做 PM 分析工作流，而不是 AI 聊天。 这个决策直接决定了： • 报告是 Tab 结构化的，不是对话流 • 输出是 JSON 约束的，不是自由文本 • 用户是"填完就走"的，不是"来回对话"的 → 这个决策也让后续的"证据驱动模式"变得自然——工作流天然支持无幻觉分支

2.3 无幻觉边界设计 核心卖点

面试官必问："AI 编的市场数据能用吗？" —— 这是你的差异化回答机会。

核心理念： AI 草稿 ≠ 已核实事实 产品必须设计边界，让用户知道"什么是 AI 编的、什么是真实的" 三层设计： 第一层：标注边界 • 所有 AI 生成的市场规模标注为"估算" • 每个模块显示"来源、假设、置信度" • 顶部固定提示："这份报告是 AI 草稿，不是已核实事实" 第二层：证据驱动模式（/evidence） • 用户手动录入证据条目（事实+来源链接+日期） • 系统只汇总已录入的证据，不调用大模型补事实 • 没有来源的模块显示"暂无已核实数据" • → 这是真正的"零幻觉"分支 第三层：自动调研 + 人工复核 • 用 Tavily API 检索真实网页 • 自动生成带来源链接的证据条目 • 但仍然提示用户："来源链接可能过期，导出前请人工复核" 产品反思： 绝对零幻觉无法单方面保证—— 因为来源本身也可能过期、偏差或被错误引用。 所以真正的解决方案不是"AI 不犯错"，而是"让用户能判断 AI 靠不靠谱"。

2.4 AI 产品方法论运用 背诵

需求分析 识别 PM 缺少"快速分析工具 + 汇报闭环"—— 不是缺数据，而是缺"从想法到结构化输出"的工作流 框架选择 把 PM 方法论产品化： • TAM/SAM/SOM → 市场分析模块 • RICE → 功能优先级模块（自动评分，1位小数） • OKR → 成功指标模块（目标+关键结果） • 风险评估 → 风险与核验模块（标注等级+影响） Prompt 工程 • 系统 Prompt 约束 JSON 输出，禁止自由文本 • 用户消息完整传入所有字段（产品想法+用户+痛点+行业+市场） • 温度 0.7，兼顾稳定性和创造性 • 代码容错：从 markdown code block 提取 JSON，缺失字段默认值 AI 产品设计三原则 1. 结构化输出 > 自由对话：Tab 布局比对话流更适合汇报 2. 标注不确定性：估算 vs 事实，置信度，来源 3. 人机协作：AI 做草稿，人做核验

2.5 最大反思：用户场景错位 体现产品思维

发现的问题 做完 MVP 后我复盘发现： 用户真正需要的不是"一份报告"，而是"一个可讨论的起点"。 为什么 • PM 做决策需要的是"团队能讨论的草稿"，不是"AI 说的真理" • 报告只是载体，价值在于"能不能快速进入讨论" • 用户反馈"有用"的不是内容本身，而是"省了我 2 小时找框架的时间" 调整方向 • 从"追求报告质量"转向"追求报告可讨论性" • 增加"反馈"按钮（有用/帮助有限），收集真实使用场景 • 增加"复制/导出"优先级——让用户能快速带入团队讨论 • 增加证据驱动模式——让用户能逐步替换 AI 草稿为真实数据 后续方向 • 报告在线编辑（让用户直接改 AI 草稿，而不是复制到文档） • 团队共享与评论（让报告进入协作流，不是个人产物） • 历史版本对比（让决策有迹可循） → 这个反思体现了"产品思维"：用户要的不是功能，而是结果

三大追问应对
面试官最可能质疑你的点，每个都准备好
Q1 为什么不直接用 ChatGPT / DeepSeek？你的差异化是什么？

答题要点：差异化不在模型，而在工作流和可信度设计。

差异化三层： 第一层：开箱即用 vs 需要 Prompt 工程 • 用 ChatGPT：你得自己写 Prompt，自己组织输出格式 • 用 InsightAI：填完就出结果，7 个维度自动结构化 第二层：框架内化 vs 用户自学 • ChatGPT 不会自动用 RICE 评分，你得告诉它怎么评 • InsightAI 把 RICE/OKR/TAM 内化为产品功能 第三层：可信度设计 vs 自由输出 • ChatGPT 的输出没有边界标注，用户不知道什么是真的 • InsightAI 有"AI 草稿"标注、证据驱动模式、来源挂载 一句话总结： ChatGPT 是"瑞士军刀"，InsightAI 是"PM 专用工具"—— 不是工具比工具强，而是场景比场景准。 → 不要否定通用 AI，而是说"场景化产品的价值在于把通用能力转化为特定工作流"
Q2 你报告里的市场数据是编的吗？怎么证明可信度？

答题要点：先承认"是 AI 估算"，再展示可信度设计。

坦诚 "是的，MVP 阶段的市场数据是 AI 估算的，这也是我最担心的问题。" 然后讲解决方案： 我设计了三层可信度机制—— 1. 标注边界 • 所有估算标注为"估算"，不冒充事实 • 显示置信度（高/中/低）和假设前提 • 顶部固定提示"这是 AI 草稿" 2. 证据驱动模式（真正的零幻觉方案） • 用户手动录入证据，系统只汇总不编造 • 没有来源的模块显示"暂无已核实数据" 3. 自动调研（接 Tavily 检索） • 自动检索真实网页，带来源链接 • 但仍提示用户人工复核 产品理念： AI 产品的可信度不是"AI 不犯错"， 而是"让用户能判断 AI 靠不靠谱"。 → 这个回答把"缺陷"转化为"设计亮点"
Q3 这个项目有真实用户吗？留存怎么样？怎么验证价值？

答题要点：诚实承认作品阶段，展示验证思路和数据埋点。

坦诚 "目前还在作品阶段，没有真实用户数据。这是我作为独立开发者的局限。" 然后讲我已经做了什么来验证—— 1. 数据埋点已设计 8 个核心事件：report_generated / tab_viewed / report_exported 等 可以追踪用户行为 2. 可度量的目标已设定 • 报告生成时间 ≤ 60 秒 ✅（已通过实测） • 报告采纳率 ≥ 60%（用户不修改直接使用） • 次日留存 ≥ 30% 3. 验证思路 如果上线，我会做： • 种子用户测试（5-10 个真实 PM） • 可用性测试（完成任务的时间和成功率） • A/B 测试（AI 草稿 vs 证据驱动） 面试亮点： 虽然没有真实数据，但我知道"有了数据之后该怎么用"。 这比"编一个好看的数据"更诚实，也更体现产品思维。 → 重点是"有度量思维"和"知道怎么验证"，而不是"有数据"

STAR 行为面试应答
面试官可能问的 5 类行为问题
STAR 1 说一个你做产品决策的经历
S：InsightAI 早期，选择"AI 聊天增强"还是"PM 分析工具" T：决定核心价值和差异化 A：竞品对比 + 3 位 PM 朋友访谈 + 框架设计 R：选择 PM 分析工作流，差异化明确，后续所有功能都基于这个定位 → 关键：用"数据/用户反馈"支撑决策，不是凭感觉
STAR 2 说一个产品失败或反思的经历
S：MVP 做完后，我发现用户真正需要的不是"一份报告" T：找出真正的用户价值 A：复盘用户反馈，发现"可讨论的起点"比"完美报告"更重要 R：调整方向——增加反馈、导出、证据驱动模式，让报告进入协作流 → 关键：反思不是"做错了"，而是"理解更深了"
STAR 3 说一个你与技术协作的经历
S：我是产品负责人，但项目用 Vibe Coding 全栈实现 T：确保技术实现符合产品设计 A：用 Chrome DevTools 实测每个功能路径， 验证 5/5 单元测试通过，0 个浏览器 JS 错误 R：产品和技术完全对齐，交付质量可验证 → 关键：技术理解让我能跟工程师"说同一种语言"
STAR 4 说一个 AI 产品设计的难点
S：AI 输出不稳定，JSON 解析经常失败 T：让 AI 输出可被前端可靠解析 A：三层容错—— 1) Prompt 约束"只输出 JSON" 2) 从 markdown code block 提取 JSON 3) 缺失字段用默认值填充 R：解析成功率从 ~60% 提升到 ~95%+ → 关键：AI 产品的"可用性"需要产品和工程双重设计
STAR 5 说一个你如何学习新东西的经历
S：需要在短时间内掌握 Vue3 + Pinia + Vite + DeepSeek API T：独立完成全栈产品 A：用 Vibe Coding 快速原型→验证→迭代， 同时深入理解每个技术选型的理由 R：2 周内完成从 0 到 1， 代码量 2724 行，测试 5/5 通过，浏览器 0 错误 → 关键：学习能力 + 执行力，这是 AI 时代 PM 的核心竞争力

反问环节
面试最后一定要问，体现思考深度
原则：不要问薪资/假期/加班。问 AI 产品方向、团队期待、成长路径。

推荐问题（按优先级排序）

  • "这个岗位的 AI 产品经理，半年内最核心的产出是什么？"
    → 了解岗位期待，展示你关注"产出"而非"流程"
  • "团队目前在 AI 产品上最大的挑战是什么？"
    → 展示你理解 AI 产品不是只有机会，还有挑战
  • "对 AI 产品经理来说，技术理解需要到什么程度？"
    → 展示你的技术背景是优势，不是劣势
  • "公司怎么衡量 AI 产品的成功？"
    → 展示你有数据驱动和结果导向的思维
